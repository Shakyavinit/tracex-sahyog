======================================================================
2. MAIN OBJECTIVE
======================================================================

Convert the current visual demo into an evidence-first SIH prototype that:

1. Accepts a suspect cryptocurrency wallet address and optional case filters.
2. Validates the address and detects the correct blockchain.
3. Fetches real on-chain transactions from verified APIs.
4. Traces outgoing fund flow through a bounded graph of 1–5 hops.
5. Finds the nearest defensible VASP deposit point by graph distance, not geographic distance.
6. Returns Top-3 probable VASP candidates, supporting evidence, source provenance, and confidence breakdown.
7. Returns UNKNOWN / NEEDS MANUAL REVIEW when the evidence is absent, conflicting, stale, or insufficient.
8. Detects known mixers, bridges, exchange wallets, deposit wallets, and suspicious laundering patterns only when supported by evidence.
9. Separates raw on-chain facts from inferred attribution.
10. Produces an investigation-ready evidence report and a mock SAHYOG request packet after human approval.

Accuracy, provenance, uncertainty, privacy, and reproducibility are more important than flashy output.

======================================================================
3. IMPORTANT MEANING OF “NEAREST VASP”
======================================================================

“Nearest” means the first supported VASP-controlled deposit or service wallet reached through the fewest defensible forward transaction hops from the suspect wallet.

- If the suspect address itself is reliably labelled as a VASP, return it as Hop 0.
- Do not continue creating intermediary wallets after a reliable Hop-0 match.
- Do not force a VASP answer when no supported labelled endpoint exists.
- Cross-chain hops must be shown as separate segments joined by a verified bridge or swap event.
- A wallet owner, beneficial owner, guilt, criminality, or legal liability must never be inferred merely from an address label.

5. REQUIRED USER FLOW
======================================================================

STEP 1 — CASE INPUT

Required fields:

- Suspect wallet address
- Network: Auto Detect, BTC, ETH, TRON, BNB, Polygon, Solana
- Case reference (synthetic or authorized value only)
- Incident date/time range
- Suspected transaction amount and asset, if known
- Crime category

Optional fields:

- Investigation note
- Transaction hash
- Direction: outgoing, incoming, both
- Maximum hop depth, default 3 and maximum 5

Do not require the investigating officer’s real name for a public SIH demo.

STEP 2 — VALIDATION

- Validate checksum/encoding with a chain-specific library, not regex alone.
- Auto-detect only when the format is unambiguous.
- EVM-format addresses are shared by ETH, BNB, and Polygon; do not claim a unique chain only from address format.
- Require network selection or inspect on-chain activity across supported EVM chain IDs.
- Invalid input must return HTTP 422 with a safe explanation.
- Do not create a history record when validation or all providers fail.

STEP 3 — REAL DATA COLLECTION

- Fetch real transactions, internal transactions, and token transfers.
- Normalize all chain responses into one internal transaction schema.
- Save raw provider response hash, source, retrieval time, network, block number, and request status.
- Never replace a failed live response with generated transactions.

STEP 4 — GRAPH TRACING

- Build a directed transaction graph.
- Trace 1–5 bounded forward hops.
- Enforce node, edge, time-window, amount, and API-budget limits.
- For EVM, handle native transfers, ERC-20/BEP-20 transfers, internal transactions, and contract calls separately.
- For Bitcoin, model UTXOs and transaction outputs correctly. Do not present account-style balances as UTXO evidence.
- Clearly label heuristics such as peel-chain, fan-out, fan-in, rapid cashout, or layering as inferences.
- Do not claim exact taint ownership when the method cannot prove it.

STEP 5 — ATTRIBUTION

- Match graph nodes to source-backed VASP, mixer, bridge, sanctions, and scam-report labels.
- Preserve provider name, source URL/reference, retrieved_at, label type, licence/use note, and last_verified_at.
- Keep raw_onchain_facts and attribution_labels in separate tables/collections.
- Never allow the same address to silently belong to conflicting VASPs.
- Display conflict and lower confidence when providers disagree.
- Stop at the first supported direct-deposit VASP sink for “nearest VASP”.

STEP 6 — ANALYST REVIEW

Return:

- Top-3 candidates or UNKNOWN
- Hop distance
- Exact supporting transaction path
- Confidence score and factor breakdown
- Source provenance and freshness
- Counter-evidence and conflicts
- Provider/API health
- Analyst actions: Accept, Reject, Needs Review

STEP 7 — REPORT

Generate:

- Investigation summary
- Raw evidence table
- Transaction path and graph
- Candidate VASPs
- Confidence explanation
- Conflicts and limitations
- Source list and retrieval timestamps
- Analyst decision and audit log
- SHA-256 report/evidence hash
- PDF and JSON export
- Mock SAHYOG request packet; do not claim a live SAHYOG connection without official credentials and API specification.

8. CONFIDENCE SCORING
======================================================================

Implement a transparent, configurable score. Do not display fake precision.

Suggested starting model:

- +50: Direct address label from an approved attribution provider
- +20: Two independent approved providers agree
- +15: Exact real transaction path reaches the labelled deposit wallet
- +10: Amount and time continuity supports the path
- +5: Behavioural cluster evidence supports the entity
- -25: Label is stale or unverified
- -40: Providers conflict
- -30: Path crosses an unresolved mixer/bridge break

Rules:

- 85–100: High confidence, still requires analyst approval
- 65–84: Probable
- 40–64: Low confidence / manual review
- Below 40: UNKNOWN
- No valid transaction evidence: UNKNOWN regardless of label score
- Provider conflict: show every candidate and conflict; never silently choose one

Display the factor-by-factor breakdown and evidence links in the UI and report. Make all weights configurable and clearly mark them as prototype policy, not a legal standard.
